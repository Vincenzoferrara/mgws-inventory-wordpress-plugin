## Inventory And Restock Foundation

The following routes are registered as stable MGWS-only contracts. Rows marked as scaffolding return `501` `mgws_not_implemented` after the documented capability check until their owning task is complete; they do not mutate stock, call a third-party provider, or expose provider details.

### Owned Tables And Migration Invariants

- Supplier identity is MGWS-only: `mg_fornitori` owns supplier id, anagrafica fields, active flag and audit fields. No WordPress user and no WooCommerce customer are created for a supplier, so a supplier can never log in or reset a password. `mg_reorder_rules` owns variant-aware reorder thresholds and preferred supplier intent.
- Suppliers are global: the `mg_fornitori` rows carry no `site_id`, supplier routes ignore any `site_id` parameter, and a site-scoped operator is not rejected with `403` when listing or reading suppliers.
- Supplier deletion is intentionally protected: a supplier referenced by a reorder rule or purchase order returns `409` `mgws_supplier_in_use`; callers can retain the historical identity and set `active: false` through PATCH instead.
- Active reorder rules emit a suggestion only when the scoped MGWS stock total is at or below `reorder_point`. A positive `reorder_quantity` is the explicit suggested quantity; otherwise the suggestion fills the gap to `target_stock`. Suggestions are planning data only.
- `mg_purchase_orders` and `mg_purchase_order_lines` own supplier-order documents and expected incoming quantities. Purchase orders begin as `draft`; Task 3 permits only `draft -> ordered`, `draft -> cancelled`, and `ordered -> cancelled`. Lines may be created or updated only while draft, or cancelled while draft/ordered without removing their identity.
- Purchase-order header and line `expected_at_gmt` accept `YYYY-MM-DDTHH:MM:SSZ` and return the stored UTC `YYYY-MM-DD HH:MM:SS` value. Every Task 3 line reports `stock_effect: incoming`; `received_qty` stays zero until the Task 4 receipt workflow posts a receipt.
- Creating, editing, cancelling, or changing status of a supplier, reorder rule, purchase order, or purchase-order line never changes `mg_stock_levels`, creates `mg_stock_moves`, or synchronizes Woo stock.
- `mg_receipts`, `mg_receipt_lines`, and `mg_backorders` own receiving/convalida state, partial quantities, and outstanding supplier quantities. Receipt lines always balance `received_qty + rejected_qty + backorder_qty = expected_qty`. Task 4 uses the documented compatible lifecycle subset `draft`, `to_receive`, `qc_hold`, `posted`, and `cancelled`; final posting records partial state on lines and creates an open backorder for every positive `backorder_qty`.
- Receipt creation and PATCH are stock-neutral. Convalida atomically rechecks that each accepted quantity still fits the linked ordered PO line, increments authoritative `mg_stock_levels` only by `received_qty`, increments PO `received_qty`, appends one `type: in`, `stock_effect: load`, `source_type: receipt` movement per accepted line with receipt/line source IDs, commits, and only then applies each accepted quantity to WooCommerce as a delta.
- A nonempty receipt idempotency key returns its existing scoped receipt on retry. A repeated convalida of a posted receipt returns that immutable receipt and creates neither another stock movement nor another stock delta.
- `mg_inventory_count_sessions` and `mg_inventory_count_lines` own physical-count drafts, book/physical discrepancy, approval identity, and eventual move link. Scans and draft lines never change stock. Approval posts only signed discrepancies after confirming each recorded book quantity still matches its live location; each adjustment uses `type: adjust`, `stock_effect: adjustment`, `source_type: inventory_count`, and session/line source IDs, then links the line's `stock_move_id`. Posted sessions and lines are immutable and duplicate approval cannot create further movements.
- Quick load is document-free: it does not require or create a supplier, purchase order, receipt, invoice, DDT, or source document. Warehouse, room, rack and shelf are optional; only supplied values override resolution. If the item has no preferred location or existing level, MGWS selects the first valid warehouse allowed by the user site scope and uses empty room/rack/shelf, so no physical detail is fabricated. Each accepted positive delta updates exactly one resolved `mg_stock_levels` location in a transaction, then appends exactly one `mg_stock_moves` row with `type: in`, `stock_effect: load`, `source_type: quick_load`, the operator user ID, the signed delta, and a note containing reason plus before/after totals. Woo stock is updated only after the MGWS transaction commits, as a delta.
- `mg_stock_reason_codes` owns site-scoped, active reason codes and their allowed stock-effect label.
- `mg_stock_moves` remains the movement audit source of truth. It gains only additive `stock_effect`, `source_type`, `source_id`, `source_line_id`, and `reason_code` metadata. Existing `type`, `ref_order_id`, and legacy rows retain their meaning.
- `mg_stock_movements` is the operation header: one row per operator action, holding the `movement_key` that groups its ledger rows, the type, operator, site, reason code, and operator note. `mg_stock_moves.movement_id` points at it and is `0` for rows written by plugin-internal flows that do not represent an operator operation. A movement is a set of rows, so a load or a reconcile of thirty products is one movement of thirty rows, and a transfer is one movement of two rows per product.
- The movement ledger reads `mg_stock_moves` only and never creates, derives, updates, or deletes movement rows. List filters are applied to authoritative rows and its newest-first order is `ts_gmt DESC, id DESC`. `stock_before` and `stock_after` are nullable columns written at audit time; rows written before those columns existed fall back to the immutable movement note, and no value is ever reconstructed from current stock or source documents.
- An audited `stock_before`/`stock_after` pair names a scope, and the scope is the one its writer measured: a reconcile records the declared site, a quick load records the item's store-wide total, and a store-wide sync records that same total. The pair is not interchangeable between places, and a counter-movement may only be written in the scope that was audited. Reversing a store-wide quick load inside one site would move a different number than the one the ledger recorded and would leave two histories disagreeing about the same stock.
- Every movement response has a typed `source` object. Receipt rows expose receipt and receipt-line IDs; inventory-count rows expose session and line IDs; quick-load rows retain `source_type: quick_load` without inventing a document; legacy POS rows retain their `ref_order_id` as `source.links.order_id`. Reconcile and other legacy rows remain readable with their stored fields and no fabricated source link.
- Schema upgrades always re-run additive `dbDelta` definitions plus idempotent `ALTER` checks for the columns added after the table was created. They do not drop, truncate, rename, or rewrite `mg_stock_levels` or `mg_stock_moves`, so fresh and upgraded installations preserve existing stock, movement rows and stock values.
- All app-facing inventory/restock endpoints are MGWS routes. Any optional provider is internal to MGWS and is never an app-visible route, request field, response field, or error detail.
- `mg_permission_sets` owns the named capability bundles: slug, label, capabilities (JSON array) and timestamps. Its `slug` is the suffix of an ordinary WordPress role `mgws_{slug}` created with `add_role()`, and the role is only the effect. The table is the source of truth; `MGWS_Permission_Sets::sync_all()` rebuilds the roles from it. `manage_options` is never stored, so no set can make an administrator, and a set in use is immutable and not deletable.

## Source Of Truth

- **Stock:** `mg_stock_levels` owns the distribution of quantity across warehouses. The WooCommerce total is written by whoever owns it for that operation: MGWS for loads, receipts, counts, transfers and admin adjustments, WooCommerce for online orders, POS sales, refunds, cancellations and order acceptance. MGWS always applies its own movements to WooCommerce as a delta, never as a total.
- **Inventory total mutations:** every total belongs to a declared scope, and the scope is never inferred. A declared `site_id` makes the write site-scoped: its `previous_stock` and `current_stock` are that site's quantities, not the item's store-wide sum, so an operator who declares the total they can see gets a zero delta. `site_id` omitted or `0` means "the one and only site", not "every site": it is accepted only on a shop with a single `mg_site`, where the item total and the site total are the same number, and is refused with `400` on a multi-site shop. A user with a site reference (`mg_default_site_id`) may reconcile only that site, and omitting `site_id` is refused to them with `403`; anyone else may reconcile any site but must still name it. Sync follows the same rule rather than being an exception: it takes the same optional `site_id`, so on a single-site shop it keeps importing the store-wide WooCommerce number with scope `0`, and on a multi-site shop it is refused with `400` unless the caller names the site, because one WooCommerce number cannot say which of several places it belongs to. Omitting `site_id` is refused with `403` to site-scoped operators on any shop, since that write would land outside their perimeter. Positive deltas use the first existing level in the deterministic level order; with no level in scope they use the item's own default warehouse when it is in the declared site, otherwise the first warehouse of that site, or the item's default location in store scope. Negative deltas consume existing levels in that same order and fail with `409` rather than go below what the scope holds.
- **Delta direction:** a total mutation writes the ledger as an absolute number and WooCommerce as a delta. On a single-site shop the delta is measured on the total WooCommerce holds at that moment, never on the number the client sent and never on the ledger: the ledger and WooCommerce are only equal while nothing has diverged, so using the ledger would add a divergence back instead of closing it, and using the payload would let a sale that happened while the operator was counting be erased. The exception is a count scoped to one site on a multi-site shop: that number describes a site, not the store, so WooCommerce moves by exactly the change of that site and a store-wide divergence stays the reconciler's job. `woo_delta_basis` on the response says which of the two was used.
- **Reconciliation:** the total and the distribution are allowed to disagree for a while, but not forever. A listener on `woocommerce_product_set_stock` / `woocommerce_variation_set_stock` compares the WooCommerce total with the sum of the levels and records the difference as an `adjust` movement, and a nightly sweep at 03:00 site time does the same for everything the listener could not see. The listener deliberately ignores the stock changes WooCommerce makes for its own orders: until the operator picks the order the goods are still on the shelf, so draining the ledger at that moment would take them from a shelf nobody chose and order acceptance would take them a second time. A positive difference is stock that exists in WooCommerce and that no shelf claims, so it lands in the site's `Unassigned` warehouse (post meta `mgws_system = 1`), which is hidden from every warehouse picker and deleted together with its site; a negative difference leaves existing levels in the deterministic level order, that warehouse first. The site of a difference is the product's declared default site, or the only site or level site that exists; on a multi-site shop with no declaration the item is left unaligned and reported rather than written to a site nobody named. A variation whose stock is managed by its parent is reconciled as one product family, because the WooCommerce number is the product total and the levels are the parts.
- **Quick loads:** quick load is additive, not reconcile-total semantics. It applies the submitted positive delta to one resolved location, preserving `mg_stock_levels` as the distribution of the quantity and `mg_stock_moves` as the audit ledger, and then applies the same delta to WooCommerce.
- **RFID scans:** a scan resolves known stored barcode values only. It never infers an `in`, `out`, `adjust`, or transfer operation from tag presence and therefore creates no stock movement.
- **Woo order linkage:** the Woo order ID returned by MGWS is the POS order authority. MGWS order meta, including `_mgws_pos_order_audit`, is the operational audit trail.
- **Movements:** `mg_stock_moves` is the movement audit source of truth, with `ref_order_id` linking POS movement records to the Woo order and `_mgws_pos_order_audit` retaining checkout context.
- **Costs:** `mg_product_costs` is the declared-cost source of truth, append-only: a correction is a new row, never an edit, so the history stays readable. A variation without its own declaration inherits the parent's; `null` means "no cost declared" and is never read as a zero. The declared cost is projected one way to WooCommerce's Cost of Goods Sold field (`_cogs_total_value`) only while that feature is enabled, and a zero is not projected because WooCommerce stores it as `null`. The projection is a convenience for order margins, not a dependency: MGWS values stock either way.
- **Money:** amounts are integer minor units, with the factor fixed at installation from `woocommerce_price_num_decimals` (`mgws_cost_minor_unit`). Changing the WooCommerce decimals later does not rescale stored values; the mismatch is reported to the administrator and new costs use the new scale.
- **Stock value:** `mg_stock_levels.stock_value_cents` is what the pieces on that level are worth, nullable and never zero-filled, because an unknown value and a worthless one are different facts. It moves with the quantity at the level's average cost: an adjustment without a cost of its own uses the current average, a receipt values the incoming pieces at the cost on the line (a legacy `0` counts as "not filled in"), and a transfer carries the source average to the destination and leaves it unknown when the source was unknown rather than inventing the receiving warehouse's average. Declaring a cost therefore changes the basis of the pieces that arrive next, not the value of the pieces already on the shelf: a revaluation is the only operation that would change value without a movement, and no route does it yet.
- **Movement costs:** `unit_cost_cents` and `value_delta_cents` on `mg_stock_moves` record what each row was valued at, so a movement can be read without replaying the levels. They are derived columns; the authoritative numbers remain `mg_product_costs` and `mg_stock_levels.stock_value_cents`.
- **Receipt cost snapshot:** `mg_pos_receipt_lines` stores `cost_total_cents` and `unit_cost_cents` per line, written at the moment of the sale or return from the allocation values the movement just applied (sale: the old value minus the outgoing value, return: the incoming value, both in minor units, with the sign the line itself uses). When a single allocation had an unreadable value the whole line stays `NULL`: a partial cost would understate the COGS and overstate the margin. `unit_cost_cents` is `ROUND(cost_total_cents / |quantity|)` and is `NULL` when the quantity is zero or the cost is unknown. The snapshot is immutable, so a later declaration never rewrites a past receipt; receipts from before the column existed keep `NULL`.
- **Margin:** the sales fact adds the line cost and derives `cost`, `margin`, `margin_rate` and `cost_coverage` (the share of covered revenue over the period net). `margin` and `margin_rate` are always published with `cost_coverage`; the online branch of the fact stays uncovered, because WooCommerce keeps `_cogs_total_value` at order level and the report cannot split it per line, so online revenue stays unknown and the coverage stays low. The margin is computed on `net_covered`, the part of net revenue whose cost is known, and is `NULL` while the cost is unknown, so a missing value is never mistaken for a free good. `revenue_share` is the period gross of one line over the period gross, which is the first step of an ABC curve without window functions.
- **Stock reports:** the `stock` source answers with a current-state aggregate of `mg_stock_levels`: `qty_on_hand`, `stock_value` (the sum of the known level values, never a null total), `unvalued_qty`, `stock_cost_coverage`, plus `sold_qty`, `rotation` and `days_without_sale` from the same sales fact. The stock measures are "now", the sold measures follow the requested period; they are not a mistake but the only honest statement without historical snapshots.

- **Permission sets:** `mg_permission_sets` owns the named capability bundles. Each row is applied as an ordinary WordPress role `mgws_{slug}` (created with `add_role()`), and the role is only the effect: the table is the source of truth, rebuilt from it by `MGWS_Permission_Sets::sync_all()`. `manage_options` is never in the catalog, so no set can make an administrator, and a set that is in use (at least one user holds its role) is immutable and not deletable. Editing or deleting a role in wp-admin is repaired on the next plugin upgrade; `remove_role()` does not detach users, which is why deletion is refused while in use. The display name is frozen at creation.
- **Stock lots:** `mg_stock_lots` and `mg_stock_lots_levels` own the grouping of pieces by origin and expiry date. A lot carries the supplier, the lot code, the expiry and the receipt date; its quantity per location is tracked separately. A lot is a label, not a movement: it creates no stock movement, changes no level quantity and carries no cost (the WAC in `mg_product_costs` stays the cost authority). `expires_at_gmt` NULL means "does not expire", `supplier_id = 0` means "unknown supplier". The sum of the level rows of a lot may be less than the location total (unlabelled stock) and is not corrected automatically.
- **Stock transfers:** `mg_stock_transfers` and `mg_stock_transfer_lines` own the stateful transfer (draft -> sent -> received, or cancelled). `sent` takes the quantity out of the source warehouse, `received` puts it into the destination, `cancelled` from `sent` compensates the source. Each transition writes its own movement rows (`source_type: stock_transfer`, `source_id` = transfer id). The instant transfer route is untouched and remains available for one-shot corrections. The quantity in transit is in no warehouse until it is received.
- **Returns:** `mg_returns` and `mg_return_lines` own the RMA (requested -> approved -> received -> refunded, or rejected from requested/approved). A return is a trail, not a stock writer: the stock total of a return/refund belongs to WooCommerce, so `receive` is stock-neutral and writes no `mg_stock_moves` row. The existing reconciler mirrors the new WooCommerce total into `mg_stock_levels`. The refund itself is not automated either: `close` only marks the return as refunded.
- **Price lists:** `mg_price_lists` and `mg_price_list_items` own the B2B price lists: a named set of per-item prices, optionally scoped to a customer or a supplier, with a validity window and a minimum quantity per tier. A price list is not the WooCommerce retail price (`_price`): it is a separate price consulted by the B2B portal and the app. It carries no stock movement and no cost. `customer_id = 0` and `supplier_id = 0` mean a generic list for all customers.
- **Approval rules:** `mg_approval_rules` owns the approval thresholds: a document type plus an amount above which a capability is required. The check is stateless and creates no record; it only answers "does this document need approval, and which capability?". Multiple rules for the same type: the most restrictive that still applies (highest threshold <= amount) wins. `threshold_cents = 0` means "always".
- **Mass stock reset:** `POST /inventory/stock/reset` is the bulk version of one adjustment, not a new authority. It writes each changed `mg_stock_levels` row to `target_qty`, appends one `adjust` movement per level (reason "Mass stock reset"), and mirrors the net per-item delta to WooCommerce through `MGWS_Woo_Stock::commit_delta()`. A level already at the target is skipped and leaves no movement, so a reset that changes nothing writes nothing. It never writes the WooCommerce total directly.
- **Supplier price history:** `mg_supplier_price_history` is append-only: the price paid or quoted by a supplier for an item, with a currency. It is not `_price` and not a WAC input, so recording a price changes no valuation; `currency` is normalised to `^[A-Z]{3}$` with `EUR` as fallback. `supplier_id` and `product_id` are required.
- **Scheduled cycle counts:** `mg_count_schedules` owns a warehouse and a frequency. The schedule decides *when*, not *what*: the daily cron at 04:00 (`mgws_run_count_schedules`) opens a draft session in `mg_inventory_count_sessions` with document number `CC-{schedule_id}-{YmdHis}` and only then moves `next_run_gmt` forward. A failed session write leaves the schedule due so the next run retries it. The manual `run-due` route does the same work with the calling user as author; the cron uses user `0`.
- **Kits:** `mg_kits` names a bundle and `mg_kit_components` lists the pieces with quantities. Defining a kit changes no level. Selling one does: WooCommerce reduces the kit product only, so MGWS takes the components from the physical site chosen by the operator (order accept, POS checkout, `POST /inventory/kits/deduct`) **and** sends the same per-component delta to WooCommerce. Without that delta the nightly reconciliation would see Woo above the ledger and put the pieces back into Unassigned. Order accept returns `kit_issues[]` when a kit line could not take all its components.
- **Documents:** `mg_documents` is metadata for DDT, invoices and credit notes: type, number, reference, status (`draft` -> `issued` -> `sent`, or `cancelled`), issue date and PDF path. The row is the record; rendering and delivery stay with the caller. `POST /inventory/purchase-orders/{id}/send` records a `purchase_order` document as `sent` and emails the supplier when an address exists; the plugin does not generate the PDF. The table is treated as fiscal and is never dropped by `uninstall.php`, even with the opt-in. Only a `draft` can be deleted; an issued document never goes back to `draft` and `cancelled` is final.
- **Payments and aging:** `mg_payments` is an amount against `reference_type`/`reference_id`, not a link to a real invoice. Aging buckets the recorded payments into `0-30`, `31-60`, `61-90` and `90+` days from `paid_at_gmt`; the route is read-only and returns minor units.
- **Shipments:** `mg_shipments` is generic over `reference_type`/`reference_id` and moves through `pending`/`shipped`/`delivered`/`cancelled`. A shipment is a trail, not a stock movement: no status change writes `mg_stock_levels` or `mg_stock_moves`.
- **Reservations:** `mg_reservations` records intent (`active` -> `released`/`consumed`). It never changes a level: releasing gives the intent back, consuming records that the intent was fulfilled. Both transitions refuse a non-`active` row with `409` `mgws_conflict`.
- **Product barcodes:** `mg_product_barcodes` keeps one code per product/variation (EAN-13, UPC-A, EAN-8 or Code 128), so a scan resolves without a product meta lookup. The table is a lookup, not an authority: it does not replace `_sku` or the WooCommerce barcode field, and writing a code changes no stock.

- **Loyalty identity:** the WordPress/Woo customer user ID is the customer and email authority. `mg_loyalty_cards` owns the nullable card number, tier, and balance snapshot; `mg_loyalty_movements` is the append-only points ledger. Card deletion clears only the card number, preserving the customer account and ledger.
- **Loyalty provider boundary:** MGWS v1 calls only its owned tables and WordPress user APIs. It does not call or expose myCred, ATUM, or any other loyalty provider.

## POS Shift And Turno Enforcement

- `mg_pos_shifts` owns the POS shift/turno lifecycle: a shift is created `open` with a unique `shift_key` (the app's turno id), a cash register `cassa_name`, journal `giornata_id`, operator, and `fondo_iniziale`; it becomes `closed` once via the close route and is never deleted.
- A cash register can have at most one `open` shift: opening a second shift for the same `cassa_name` returns `409` `mgws_shift_already_open`; a duplicate `shift_key` always returns `409` `mgws_shift_conflict`.
- POS checkout is strictly shift-gated: every `/pos/checkout` must reference an `open` shift via root `shift_id` (fallback metadata `_turno_id`). A missing, unknown, or closed shift returns `409` (`mgws_shift_required`, `mgws_shift_not_found`, `mgws_shift_closed`) before any stock, order, or idempotency write. The idempotent replay of an already-recorded checkout succeeds after the shift closes.
- Every checkout order stores `_mgws_shift_id` (the `mg_pos_shifts.id`) and `_mgws_shift_key`, making the shift the authoritative grouping unit for POS sales and returns.
- The close route computes `expected_totals` server-side from the shift's orders (Woo orders carrying `_mgws_shift_id`), bucketed by payment method (`contanti`, `carta`/`bancomat`, other) for non-negative totals and refunds for negative totals; cancelled/draft/failed orders are excluded. The client never dictates expected totals.
- The closure record persists `expected_totals`, the physical `contato` values, and `differenze` (`contante_atteso = fondo_iniziale + contanti`, `carta_atteso = carta`); a non-zero difference is informational and does not block the closure. `causale_differenza` is optional at the API level.

## POS Checkout Idempotency

- A nonempty root `idempotency_key` is authoritative. If it is absent, MGWS uses the first `meta_data` entry with key `_id_scontrino_locale`. Requests without either key remain supported for legacy compatibility but do not have replay guarantees.
- For a keyed request, MGWS validates products and builds the stock allocation plan before atomically reserving `mg_pos_idempotency.idempotency_key`, and always reserves before `wc_create_order()`.
- The payload hash is SHA-256 of canonical JSON. It includes `sale_items`, `return_items`, `customer`, `totals`, payment method/title, operation type/effective type, `set_paid`, `note`, and remaining `meta_data`. Associative object keys are sorted recursively; numeric arrays retain their submitted order.
- The hash excludes the root `idempotency_key`, metadata `_id_scontrino_locale`, and volatile timestamps: root `timestamp`, `created_at`, `created_at_gmt`, `updated_at`, `updated_at_gmt`, and `sent_at`; metadata `_data_operazione`, `timestamp`, `created_at`, `created_at_gmt`, `updated_at`, `updated_at_gmt`, and `sent_at`.
- Reusing a key with the same hash returns the stored successful checkout response and the original Woo order ID without creating an order or stock movements. Reusing it with a different hash returns `409` with `mgws_idempotency_conflict` and makes no mutation.
- A concurrent duplicate that finds a matching `processing` reservation returns `409` with `mgws_idempotency_in_progress`. After the first request finishes, the same request replays the stored success result.
- Validation failures before reservation leave no idempotency record. Failures after reservation are stored as `failed` with deterministic error code, HTTP status, and recovery state; a later same-key retry returns that failure and never replays success.

## Validation And Path Safety

- Inventory, loyalty, and POS routes register explicit REST argument schemas with sanitize and validation callbacks. Route-level validation occurs before a mutation callback; handlers repeat the critical checks for internal/direct calls.
- Numeric identifiers and quantities accept only decimal integers in their documented range. Malformed values return `400` before WooCommerce, stock, loyalty, or idempotency writes.
- Loyalty card and email lookups use exactly one URL-decoded path segment. Clients must URI-encode card numbers and emails with `Uri.encodeComponent`; the server validates the decoded card/email and never echoes malformed lookup input.
- Authentication failures return `401`; authenticated callers without the route capability receive `403`. POS, inventory, and loyalty keep their documented route-specific callbacks and do not expose an application-level provider bypass.
- Public error messages are stable. Checkout failure and replay responses do not expose SQL, exception text, file paths, tokens, passwords, Woo secrets, raw malformed lookup input, or unrelated customer data.
