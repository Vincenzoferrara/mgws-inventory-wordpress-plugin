### Owned Tables And Migration Invariants

- Supplier identity is MGWS-only: `mg_fornitori` owns supplier id, anagrafica fields, active flag and audit fields. No WordPress user and no WooCommerce customer are created for a supplier, so a supplier can never log in or reset a password. `mg_reorder_rules` owns variant-aware reorder thresholds and preferred supplier intent.
- Suppliers are global: the `mg_fornitori` rows carry no `site_id`, supplier routes ignore any `site_id` parameter, and a site-scoped operator is not rejected with `403` when listing or reading suppliers.
- Supplier deletion is intentionally protected: a supplier referenced by a reorder rule or purchase order returns `409` `mgws_supplier_in_use`; callers can retain the historical identity and set `active: false` through PATCH instead.
- Active reorder rules emit a suggestion only when the scoped MGWS stock total is at or below `reorder_point`. A positive `reorder_quantity` is the explicit suggested quantity; otherwise the suggestion fills the gap to `target_stock`. Suggestions are planning data only.
- `mg_purchase_orders` and `mg_purchase_order_lines` own supplier-order documents and expected incoming quantities. Purchase orders begin as `draft`; Task 3 permits only `draft -> ordered`, `draft -> cancelled`, and `ordered -> cancelled`. Lines may be created or updated only while draft, or cancelled while draft/ordered without removing their identity.
- Purchase-order header and line `expected_at_gmt` accept `YYYY-MM-DDTHH:MM:SSZ` and return the stored UTC `YYYY-MM-DD HH:MM:SS` value. Every Task 3 line reports `stock_effect: incoming`; `received_qty` stays zero until the Task 4 receipt workflow posts a receipt.
- Creating, editing, cancelling, or changing status of a supplier, reorder rule, purchase order, or purchase-order line never changes `mg_stock_levels`, creates `mg_stock_moves`, or synchronizes Woo stock.
- `mg_receipts`, `mg_receipt_lines`, and `mg_backorders` own receiving/convalida state, partial quantities, and outstanding supplier quantities. Receipt lines always balance `received_qty + rejected_qty + backorder_qty = expected_qty`. Task 4 uses the documented compatible lifecycle subset `draft`, `to_receive`, `qc_hold`, `posted`, and `cancelled`; final posting records partial state on lines and creates an open backorder for every positive `backorder_qty`.
- Receipt creation and PATCH are stock-neutral. Convalida atomically rechecks that each accepted quantity still fits the linked ordered PO line, increments authoritative `mg_stock_levels` only by `received_qty`, increments PO `received_qty`, appends one `type: in`, `stock_effect: load`, `source_type: receipt` movement per accepted line with receipt/line source IDs, commits, and only then projects each affected total to Woo.
- A nonempty receipt idempotency key returns its existing scoped receipt on retry. A repeated convalida of a posted receipt returns that immutable receipt and creates neither another stock movement nor another stock delta.
- `mg_inventory_count_sessions` and `mg_inventory_count_lines` own physical-count drafts, book/physical discrepancy, approval identity, and eventual move link. Scans and draft lines never change stock. Approval posts only signed discrepancies after confirming each recorded book quantity still matches its live location; each adjustment uses `type: adjust`, `stock_effect: adjustment`, `source_type: inventory_count`, and session/line source IDs, then links the line's `stock_move_id`. Posted sessions and lines are immutable and duplicate approval cannot create further movements.
- Quick load is document-free: it does not require or create a supplier, purchase order, receipt, invoice, DDT, or source document. Warehouse, room, rack and shelf are optional; only supplied values override resolution. If the item has no preferred location or existing level, MGWS selects the first valid warehouse allowed by the user site scope and uses empty room/rack/shelf, so no physical detail is fabricated. Each accepted positive delta updates exactly one resolved `mg_stock_levels` location in a transaction, then appends exactly one `mg_stock_moves` row with `type: in`, `stock_effect: load`, `source_type: quick_load`, the operator user ID, the signed delta, and a note containing reason plus before/after totals. Woo stock is synchronized only after the MGWS transaction commits.
- `mg_stock_reason_codes` owns site-scoped, active reason codes and their allowed stock-effect label.
- `mg_stock_moves` remains the movement audit source of truth. It gains only additive `stock_effect`, `source_type`, `source_id`, `source_line_id`, and `reason_code` metadata. Existing `type`, `ref_order_id`, and legacy rows retain their meaning.
- `mg_stock_movements` is the operation header: one row per operator action, holding the `movement_key` that groups its ledger rows, the type, operator, site, reason code, and operator note. `mg_stock_moves.movement_id` points at it and is `0` for rows written by plugin-internal flows that do not represent an operator operation. A movement is a set of rows, so a load or a reconcile of thirty products is one movement of thirty rows, and a transfer is one movement of two rows per product.
- The movement ledger reads `mg_stock_moves` only and never creates, derives, updates, or deletes movement rows. List filters are applied to authoritative rows and its newest-first order is `ts_gmt DESC, id DESC`. `stock_before` and `stock_after` are nullable columns written at audit time; rows written before those columns existed fall back to the immutable movement note, and no value is ever reconstructed from current stock or source documents.
- An audited `stock_before`/`stock_after` pair names a scope, and the scope is the one its writer measured: a reconcile records the declared site, a quick load records the item's store-wide total, and a store-wide sync records that same total. The pair is not interchangeable between places, and a counter-movement may only be written in the scope that was audited. Reversing a store-wide quick load inside one site would move a different number than the one the ledger recorded and would leave two histories disagreeing about the same stock.
- Every movement response has a typed `source` object. Receipt rows expose receipt and receipt-line IDs; inventory-count rows expose session and line IDs; quick-load rows retain `source_type: quick_load` without inventing a document; legacy POS rows retain their `ref_order_id` as `source.links.order_id`. Reconcile and other legacy rows remain readable with their stored fields and no fabricated source link.
- Schema version 8 always re-runs additive `dbDelta` definitions. It does not drop, truncate, rename, or rewrite `mg_stock_levels` or `mg_stock_moves`, so fresh and upgraded installations preserve existing stock and movement rows.
- All app-facing inventory/restock endpoints are MGWS routes. Any optional provider is internal to MGWS and is never an app-visible route, request field, response field, or error detail.

## Source Of Truth

- **Stock:** `mg_stock_levels` is the quantity source of truth. WooCommerce stock is a synchronized projection, not the inventory authority.
- **Inventory total mutations:** every total belongs to a declared scope, and the scope is never inferred. A declared `site_id` makes the write site-scoped: its `previous_stock` and `current_stock` are that site's quantities, not the item's store-wide sum, so an operator who declares the total they can see gets a zero delta. `site_id` omitted or `0` means "the one and only site", not "every site": it is accepted only on a shop with a single `mg_site`, where the item total and the site total are the same number, and is refused with `400` on a multi-site shop. A user with a site reference (`mg_default_site_id`) may reconcile only that site, and omitting `site_id` is refused to them with `403`; anyone else may reconcile any site but must still name it. Sync follows the same rule rather than being an exception: it takes the same optional `site_id`, so on a single-site shop it keeps importing the store-wide WooCommerce number with scope `0`, and on a multi-site shop it is refused with `400` unless the caller names the site, because one WooCommerce number cannot say which of several places it belongs to. Omitting `site_id` is refused with `403` to site-scoped operators on any shop, since that write would land outside their perimeter. Positive deltas use the first existing level in the deterministic level order; with no level in scope they use the item's own default warehouse when it is in the declared site, otherwise the first warehouse of that site, or the item's default location in store scope. Negative deltas consume existing levels in that same order and fail with `409` rather than go below what the scope holds.
- **Quick loads:** quick load is additive, not reconcile-total semantics. It applies the submitted positive delta to one resolved location, preserving `mg_stock_levels` as authority and `mg_stock_moves` as the audit ledger before projecting the resulting item total to Woo.
- **RFID scans:** a scan resolves known stored barcode values only. It never infers an `in`, `out`, `adjust`, or transfer operation from tag presence and therefore creates no stock movement.
- **Woo order linkage:** the Woo order ID returned by MGWS is the POS order authority. MGWS order meta, including `_mgws_pos_order_audit`, is the operational audit trail.
- **Movements:** `mg_stock_moves` is the movement audit source of truth, with `ref_order_id` linking POS movement records to the Woo order and `_mgws_pos_order_audit` retaining checkout context.
- **Loyalty identity:** the WordPress/Woo customer user ID is the customer and email authority. `mg_loyalty_cards` owns the nullable card number, tier, and balance snapshot; `mg_loyalty_movements` is the append-only points ledger. Card deletion clears only the card number, preserving the customer account and ledger.
- **Loyalty provider boundary:** MGWS v1 calls only its owned tables and WordPress user APIs. It does not call or expose myCred, ATUM, or any other loyalty provider.

## POS Shift And Turno Enforcement

- `mg_pos_shifts` owns the POS shift/turno lifecycle: a shift is created `open` with a unique `shift_key` (the app's turno id), a cash register `cassa_name`, journal `giornata_id`, operator, and `fondo_iniziale`; it becomes `closed` once via the close route and is never deleted.
- A cash register can have at most one `open` shift: opening a second shift for the same `cassa_name` returns `409` `mgws_shift_already_open`; a duplicate `shift_key` always returns `409` `mgws_shift_conflict`.
- POS checkout is strictly shift-gated: every `/pos/checkout` must reference an `open` shift via root `shift_id` (fallback metadata `_turno_id`). A missing, unknown, or closed shift returns `409` (`mgws_shift_required`, `mgws_shift_not_found`, `mgws_shift_closed`) before any stock, order, or idempotency write. The idempotent replay of an already-recorded checkout succeeds after the shift closes.
- Every checkout order stores `_mgws_shift_id` (the `mg_pos_shifts.id`) and `_mgws_shift_key`, making the shift the authoritative grouping unit for POS sales and returns.
- The close route computes `expected_totals` server-side from the shift's orders (Woo orders carrying `_mgws_shift_id`), bucketed by payment method (`contanti`, `carta`/`bancomat`, other) for non-negative totals and refunds for negative totals; cancelled/draft/failed orders are excluded. The client never dictates expected totals.
- The closure record persists `expected_totals`, the physical `contato` values, and `differenze` (`contante_atteso = fondo_iniziale + contanti`, `carta_atteso = carta`); a non-zero difference is informational and does not block the closure. `causale_differenza` is optional at the API level.

## POS Checkout Idempotency

- A nonempty root `idempotency_key` is authoritative. If it is absent, MGWS uses the first `meta_data` entry with key `_id_scontrino_locale`. Requests without either key remain supported for legacy compatibility but do not have replay guarantees.
- For a keyed request, MGWS validates products and builds the stock allocation plan before atomically reserving `mg_pos_idempotency.idempotency_key`, and always reserves before `wc_create_order()`.
- The payload hash is SHA-256 of canonical JSON. It includes `sale_items`, `return_items`, `customer`, `totals`, payment method/title, operation type/effective type, `set_paid`, `note`, and remaining `meta_data`. Associative object keys are sorted recursively; numeric arrays retain their submitted order.
- The hash excludes the root `idempotency_key`, metadata `_id_scontrino_locale`, and volatile timestamps: root `timestamp`, `created_at`, `created_at_gmt`, `updated_at`, `updated_at_gmt`, and `sent_at`; metadata `_data_operazione`, `timestamp`, `created_at`, `created_at_gmt`, `updated_at`, `updated_at_gmt`, and `sent_at`.
- Reusing a key with the same hash returns the stored successful checkout response and the original Woo order ID without creating an order or stock movements. Reusing it with a different hash returns `409` with `mgws_idempotency_conflict` and makes no mutation.
- A concurrent duplicate that finds a matching `processing` reservation returns `409` with `mgws_idempotency_in_progress`. After the first request finishes, the same request replays the stored success result.
- Validation failures before reservation leave no idempotency record. Failures after reservation are stored as `failed` with deterministic error code, HTTP status, and recovery state; a later same-key retry returns that failure and never replays success.

## Validation And Path Safety

- Inventory, loyalty, and POS routes register explicit REST argument schemas with sanitize and validation callbacks. Route-level validation occurs before a mutation callback; handlers repeat the critical checks for internal/direct calls.
- Numeric identifiers and quantities accept only decimal integers in their documented range. Malformed values return `400` before WooCommerce, stock, loyalty, or idempotency writes.
- Loyalty card and email lookups use exactly one URL-decoded path segment. Clients must URI-encode card numbers and emails with `Uri.encodeComponent`; the server validates the decoded card/email and never echoes malformed lookup input.
- Authentication failures return `401`; authenticated callers without the route capability receive `403`. POS, inventory, and loyalty keep their documented route-specific callbacks and do not expose an application-level provider bypass.
- Public error messages are stable. Checkout failure and replay responses do not expose SQL, exception text, file paths, tokens, passwords, Woo secrets, raw malformed lookup input, or unrelated customer data.
